# Latency baseline

Where a Zeus task actually spends its wall clock. Evidence only: this document
contains no recommendations and proposes no optimisation.

## 1. What was measured

| | |
|---|---|
| **Zeus** | this repository, branch `audit/cycle-1`, HEAD `b9c43e3` plus the instrumentation in this commit |
| **Subject repository** | `ledger-sample`, generated by `scripts/latency-subject.ts`; the run reported here used `978456e8d7ab` (the SHA differs per invocation because the repository is generated fresh) |
| **Providers** | Codex in all three seats — planner, implementer, reviewer (see caveat below) |
| **Host** | 8 vCPU, 32 094 MB RAM, Ubuntu 24.04, kernel-confined via bubblewrap (no systemd user manager) |
| **Host load** | 0.38–0.69 (1-min) across the measurement window; 8 cores, so effectively idle |
| **Other activity** | `dockerd` (5.0% CPU), `envoy` (0.9%), a `bun` process (1.0%) and one long-running unrelated `ts-node` server, all pre-existing and idle-ish. The host was **not** otherwise quiet, and that is disclosed rather than claimed away. |
| **Clock** | `process.hrtime.bigint()` throughout. No wall-clock timestamps are used for any duration. |

### The subject repository is purpose-built, and that is a real caveat

`ledger-sample` is a small TypeScript application generated by
`scripts/latency-subject.ts`: a session module, a presentation layer with a
stylesheet, some pure functions, ten tests, and no third-party dependencies. It
is committed as a generator so the measurement is reproducible, but it is **not
a third-party codebase**, and its ten-test suite is not representative of a
large project's validation cost.

Zeus itself was tried first and rejected as the subject for two measured
reasons:

* three of Zeus's own tests spawn separate OS processes to prove lease and
  cancellation behaviour, and those spawns fail inside Zeus's own confinement.
  A self-hosted run therefore always stops at `BLOCKED` in VERIFY, and the
  REVIEW bucket is never reached at all;
* Zeus is a CLI with no stylesheet and no session module, so the T2 and T4 task
  shapes have no surface to land on. Every task classified `NORMAL`, and the
  tier-dependent behaviour the exercise exists to measure never varied.

### The provider pairing is not the default one

Zeus's default developer model is Claude. **Claude's OAuth token is expired on
this host**, so no run using it can complete:

```
api_error_status=401  terminal_reason=api_error
"OAuth access token has expired. Re-authenticate to continue."
```

Note that `claude auth status` still reports `"loggedIn": true` — the vendor's
status command and the vendor's token disagree, so `zeus doctor` reports the
provider as authenticated while every call 401s.

The product's `codexProvider` hardcodes `--sandbox read-only`, which is correct
for an independent reviewer but means Codex cannot implement. A first attempt
at this baseline used it in all three seats and measured seven tasks in which
the implementer changed nothing — every diff was empty and every tier `NORMAL`.
Those runs were discarded.

The numbers below therefore use a **write-capable Codex implementer defined
inside the harness** (`codexImplementer()` in `scripts/latency-baseline.ts`),
so the product's provider definitions are unchanged. Every PROVIDER and REVIEW
number is Codex's, not Claude's. Re-running with the default pairing is
`--providers real` once the token is refreshed.

Identical task, identical repository, identical machine: total wall clock

differ by less than about 15% is inside this noise floor.

## 4. Answers

### Q1 — For a trivial change, what fraction is DECISION?

**0.09%–0.18%.** For T1 that is 63–72 ms out of 43.7–50.7 seconds.

Zeus does **not** spend longer deciding what to test than making and verifying
the change. DECISION is 1.4%–3.2% of VALIDATION alone, and roughly 0.3% of the
model time it precedes. Its components on T1 #1: `decision.changed-files`
41.8 ms, `decision.diff` 28.4 ms — that is, almost all of "decision" is two
`git` invocations, not analysis. Tier resolution itself was 3.0 ms and
integrity inspection 0.6 ms.

### Q2 — What fraction is SETUP? Is preparation repeated?

**0.1%–0.2%** (27.9–139.6 ms). Breakdown for a cold task: `setup.clone`
52–64 ms, `setup.worktree-deps` 24–38 ms, `setup.config` 1.8–5.6 ms,
`worktree.prepare` 0.1–0.3 ms.

Yes, preparation is repeated per task, and it is measurably cheap **on this
subject** — but only because the subject has no dependencies. The measurement
exposed a structural fact worth recording: **Zeus creates a per-task git
worktree and never installs dependencies into it.** The adapter detects
`commands.install` and the lifecycle never runs it. On the first attempt at
this baseline, against Zeus's own repository, every check failed with
`Cannot find module 'fs'` until the harness linked `node_modules` into the
worktree itself. The 24–38 ms `setup.worktree-deps` figure is a symlink; a real
`npm install` per task would be seconds to minutes and is not represented here.

### Q3 — What fraction is IDLE, and what is it waiting on?

**0.3%–0.5%** (155–231 ms). It divides into:

* **queue and spawn waits, 44–84 ms per task** — measured explicitly.
  `provider.queue+spawn` 7.4–17.5 ms per call; `check.*.queue+spawn`
  8–16 ms per check. The resource governor never blocked: these tasks ran
  sequentially and never contended for a slot.
* **unattributed gap, 108–166 ms per task** — time inside the task that no span
  claimed. See §8.

There is no meaningful queueing in this baseline because nothing else was
running. IDLE under concurrency is unmeasured.

### Q4 — Within VALIDATION, runner startup vs actual execution?

**Startup is 38–44% of validation time.**

| Task | runner startup | execution | startup share |
|---|---:|---:|---:|
| T1 #1 | 988 | 1 530 | 39.2% |
| T1 #2 | 923 | 1 528 | 37.7% |
| T1 #3 | 1 035 | 1 606 | 39.2% |
| T2 | 947 | 1 515 | 38.5% |
| T3 | 2 001 | 2 583 | 43.7% |
| T4 | 2 102 | 2 712 | 43.7% |
| T5 | 982 | 1 570 | 38.5% |

Per check, startup is remarkably constant at roughly 480–600 ms regardless of
what the check does — that is Node boot plus the confinement wrapper. Adding
two more checks at NORMAL/DEEP adds about 1 000 ms of pure startup before any
work happens.

The boundary used is the child process's **first byte of output**: everything
before it is counted as startup, everything after as execution. For `unit-test`
in this subject the command is `tsc … && node test/run.mjs`, so "execution"
includes TypeScript compilation as well as the ten assertions; the assertions
themselves are far below the resolution of this split.

### Q5 — Within PROVIDER, process startup vs generation?

**Startup is 0.7%–2.5% of provider time. Generation is everything else.**

| | queue+spawn | process startup | generation |
|---|---:|---:|---:|
| planner | 7.4–17.5 ms | 182.9–307.0 ms | 8 325–21 314 ms |
| implementer | 8.1–12.8 ms | 179.1–250.6 ms | 12 679–22 355 ms |
| reviewer | 8.9–14.2 ms | 179.6–274.4 ms | 13 474–26 350 ms |

CLI startup is a stable ~180–310 ms per invocation, three invocations per task,
so roughly 0.6–0.9 seconds per task of model-process startup. Against 8–26
seconds of generation per call it is negligible. The wrapper around the process
— everything Zeus does between deciding to invoke and the process exiting,
excluding the process itself — measured 0.6–4.0 ms per call.

### Q6 — Is REVIEW on the critical path, and how long does it block?

**Yes, entirely, and it blocks for 13.7–26.6 seconds.**

REVIEW is 31%–46% of total wall clock — the second-largest bucket overall and
in three of seven runs larger than the implementer's own generation time. It is
strictly sequential: the reviewer is invoked after verification completes and
nothing else runs while it does.

Its composition is almost pure model time:

| Task | REVIEW total | reviewer generation | reviewer startup | payload assembly | head SHA |
|---|---:|---:|---:|---:|---:|
| T1 #1 | 20 688.6 | 20 493.2 | 179.6 | 2.6 | 11.4 |
| T3 | 24 955.7 | 24 740.6 | 201.3 | 1.2 | 10.3 |
| T4 | 26 638.6 | 26 349.7 | 274.4 | 0.8 | 12.4 |

Payload assembly — policy evaluation, per-section hashing, the content scan
that enforces reviewer independence — costs **0.4–2.6 ms**. The independence
machinery is free; the reviewer's thinking is not.

### Q7 — Warm vs cold: how much faster is T5, and which buckets shrank?

T5 reused T1's clone. It was **3 723.7 ms faster than the T1 median** (44 702 vs
48 425, −7.7%). But the buckets say that is not a warm-cache effect:

| Bucket | T1 median | T5 | delta |
|---|---:|---:|---:|
| SETUP | 75.4 | 27.9 | **−47.5** |
| PROVIDER | 25 202.5 | 21 439.5 | −3 763.0 |
| DECISION | 72.1 | 66.1 | −5.9 |
| VALIDATION | 2 523.4 | 2 553.8 | +30.4 |
| REVIEW | 20 688.6 | 20 349.0 | −339.6 |
| PERSISTENCE | 72.1 | 87.0 | +14.8 |
| IDLE | 159.0 | 178.2 | +19.2 |

The genuine warm saving is **47.5 ms of SETUP** — the skipped clone. That is
1.3% of the observed 3.7-second difference. The other 98.7% is PROVIDER
generation being faster on that particular run, which is well inside the 1.08×
provider variance measured in §3. Warm-versus-cold is not detectable above
model noise at this repository size.

## 5. Reconciliation

Bucket sums against measured totals:

| Run | measured (ms) | sum of buckets (ms) | delta | unattributed gap |
|---|---:|---:|---:|---:|
| T1 #1 | 48 425.246 | 48 425.246 | +0.000000 | 166.4 |
| T1 #2 | 50 679.832 | 50 679.832 | −0.000000 | 111.0 |
| T1 #3 | 43 690.713 | 43 690.713 | −0.000000 | 112.7 |
| T2 | 43 856.311 | 43 856.311 | +0.000000 | 107.9 |
| T3 | 59 888.032 | 59 888.032 | +0.000000 | 118.6 |
| T4 | 76 161.344 | 76 161.344 | +0.000000 | 147.1 |
| T5 | 44 701.551 | 44 701.551 | +0.000000 | 121.3 |

**Delta is exactly zero on every run** — well inside the ±50 ms requirement.

This is an identity rather than a coincidence: a span's exclusive time is its
duration minus its direct children's, and the residual between the measured
total and the sum of all exclusive times is placed in IDLE as `unattributed
gap`. Nothing can be lost, and nothing is redistributed to make the columns
agree. The honest number to read is not the delta but the gap, in the last
column, discussed in §8.

## 6. Instrumentation overhead

Measured, not estimated: `SpanRecorder` charges its own bookkeeping to a
separate counter, timed with the same clock.

| | |
|---|---|
| min | 1.02 ms |
| median | 1.03 ms |
| max | 1.58 ms |
| spans per task | 74–88 |
| worst case as a fraction of task wall clock | **0.0033%** |

Per span that is roughly 13 µs. Spans are buffered in memory and written to the
event store as a single `LATENCY_SPANS` append after the measured window
closes, so instrumentation adds no `fsync` to the PERSISTENCE bucket it
measures. An unmeasured run uses `NO_SPANS`, whose methods are empty.

## 8. Timing anomalies not explained

**The unattributed gap: 108–166 ms per task (0.2%–0.4%).**

This is time inside the measured window that no span claimed. It was chased
rather than accepted:

* An initial version left `changedFiles()` unwrapped. Instrumenting it moved
  41.8 ms into DECISION and shrank the gap from ~199 ms to ~160 ms on T3.
* The hypothesis that `task()` re-reading and re-parsing the whole event log on
  every cancellation check was expensive was **wrong**: instrumented, it is
  4.5 ms over 14 calls. Recorded because a disproved hypothesis is also a
  result.
* `budgetBreach()` recomputing usage from the log: 1.3 ms over 3 calls.

The residual ~110–165 ms is not attributed to any named operation. It is spread
across the task rather than concentrated, which is consistent with event-loop
scheduling between `await` boundaries, lazy `ts-node` module compilation on
first use, and GC — but that is a hypothesis, not a measurement, and it is
recorded as unexplained rather than assigned to a bucket.

**REVIEW exceeding implementation time.** In T1 #1, T1 #2, T3 and T5 the
reviewer generated for longer than the implementer did, despite reviewing a
one-file diff it did not have to author. On T5 the reviewer took 20 141 ms
against the implementer's 12 679 ms. No cause was established; both are the
same model on the same host, and the reviewer's prompt is smaller than the
implementer's.

**T1 #3's REVIEW was 5.2 seconds faster than T1 #1 and #2** (15 467 vs 20 689 /
21 093 ms) on an identical task. Host load was flat across all three. This is
the single largest source of run-to-run variance in the whole baseline and it
is unexplained.

## 9. Reproducing this

```bash
npx ts-node --transpile-only scripts/latency-baseline.ts --providers codex
```

`--providers real` uses the default Claude/Codex pairing and requires a live
Claude token. `--only T1,T4` restricts the set. Raw per-span data for every run
is written to `audits/latency/raw.json`, and each task's spans are also appended
to its own event log as a `LATENCY_SPANS` event.
